# Flood Relief Dashboard — Bengaluru Ward-Level Flood Risk

An AI-driven Flask application that combines a **local geospatial Random
Forest model** with a **cloud-hosted LLM** to predict ward-level urban flood
risk in Bengaluru and translate the technical output into localized,
actionable public safety advisories.

This is a rebuild/consolidation of the uploaded `Project-16(PES)` codebase:
the original had many experimental copies of the same app (`app.py` …
`app4.py`, `predict.py` … `predict8.py`, `index.html` … `index6.html` across
`demo/`, `demo1/`, and the project root) and, critically, the "final"
predictor never actually called the trained model — `predict_final.py` used
a hand-written heuristic score instead. This version fixes that, and adds
the LLM advisory layer the spec asked for, which didn't exist yet.

## Architecture

```
Terrain (elevation) + Drainage (KML) + Census 2011  ──▶  feature engineering
                                                              │
                                          18 engineered features per ward
                                                              │
                                     RandomForestClassifier (300 trees,
                                     max_depth 15, trained locally, offline)
                                                              │
                                     risk class: Low / Medium / High
                                                              │
                         + live rainfall (Open-Meteo) nudges the prediction
                                                              │
                              evacuation state: MONITOR / PREPARE / EVACUATE
                                                              │
                          Claude (Anthropic Messages API) turns the numbers
                          into a short, ward-specific public safety advisory
```

- **Local ML** (`predictor.py`): loads `flood_risk_model.pkl` (a
  `RandomForestClassifier` trained on `mean/min/max elevation`,
  `total_drainage_m`, `avg_annual_rainfall`, population/gender/SC/ST counts,
  and derived ratios — 18 features total, see `data/feature_names.json`),
  scales the feature vector with the fitted `StandardScaler`, and predicts a
  risk class. This runs entirely offline — no API key needed to get a risk
  number.
- **Live signal**: on each ward lookup, the app fetches the latest hourly
  precipitation reading from Open-Meteo for that ward's centroid and folds
  it into the rainfall feature before re-scoring, so the risk reacts to
  what's happening right now, not just the static 2011 census baseline.
- **Evacuation state**: a rule layer combines the risk class with local
  vulnerability signals (population density, drainage density, SC/ST
  population ratio) to produce an operational state — `MONITOR`, `PREPARE`,
  or `EVACUATE` — the kind of decision a ward disaster-management officer
  needs, not just a risk label.
- **LLM advisory** (`advisory.py`): calls Claude via the Anthropic Messages
  API with the ward's specific metrics and asks for a short, plain-language,
  actionable advisory. If `ANTHROPIC_API_KEY` isn't set (or the call fails),
  it falls back to a deterministic templated advisory so the app still works
  end-to-end offline.

## Setup

```bash
cd flood_dashboard
pip install -r requirements.txt

# Optional — without this, advisories use the offline template fallback
export ANTHROPIC_API_KEY=sk-ant-...

python app.py
```

Then open http://localhost:5000.

## Project layout

```
app.py          Flask routes (map data, per-ward prediction, advisory)
predictor.py    Feature loading + Random Forest inference + evacuation logic
advisory.py     LLM advisory generation with offline fallback
data/           Trained model, scaler, feature list, pre-engineered ward geojson
templates/      index.html
static/         app.js, style.css
```

## Known data limitations (inherited from the source dataset, documented honestly)

- `mean_elevation` is `0` for every ward — the DEM zonal-statistics step in
  the original pipeline (`backend/process_data.py`) never ran against a real
  elevation raster, so this feature currently contributes nothing to the
  model's split decisions. If you have access to a real Bengaluru DEM,
  re-running `process_data.py` (a real PostGIS + rasterio pipeline is
  already present, just needs a `DATABASE_URL` and a real `.tif`) would
  materially improve the model.
- `avg_annual_rainfall` is a flat 960mm for every ward (dataset-wide
  average, not ward-specific), which is why the live Open-Meteo reading is
  weighted in as a deliberate amplifier (`LIVE_RAINFALL_AMPLIFIER` in
  `predictor.py`) rather than blended in proportionally — it's a documented
  heuristic, not a calibrated meteorological model.
- Class labels (Low/Medium/High) were generated by binning a composite
  score built from elevation, drainage, vulnerability, and rainfall
  percentiles (see the original `train7.py`), not from historical flood
  incident records — reasonable for a capstone/demo, but worth stating
  explicitly if you're writing this up for a report or publication.

## Extending this for award/publication framing

If you're pursuing the "award-competitive / publishable" angle: the
strongest, least-crowded contribution here isn't the Random Forest itself
(ward flood-risk classification from census+terrain+drainage features is
well-trodden) — it's the **evacuation-state reasoning + LLM
localization layer** on top of it. Consider foregrounding that in any
writeup, and citing this as an agentic decision-support layer over a
conventional classifier, similar to the framing used for your earlier
methane-detection project.
